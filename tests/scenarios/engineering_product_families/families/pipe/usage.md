# PIPE Family candidate

## Inputs and output

Self geometry requires two standard `external_constraints`, keyed `inlet` and `outlet`, each with a `fixed_point` condition containing `point_m`, a nonzero `axis`, and `outer_diameter_m`. Both diameters must be equal and positive; this Family does not create transitions. `middle_points_m` retains the ordered source vertices between those endpoints, in project-world metres, and may be empty for a straight path. The Program assembles the full path once from the two targets and those middle vertices. Position and OD are not repeated in public product parameters. `section.known_wall_thickness_m=[]` preserves an unknown wall; `[t]` selects a real annular section with known `0<t<OD/2`. `product_origin` remains the separate METRE installation origin. All values must be finite, and every adjacent path segment must be positive.

The condition axis is the external datum's outward axis. With the default `direction_relation: opposed`, inlet uses the first forward path tangent and outlet uses the negative last tangent. Explicit `same` instead supplies the actual product outward axes. The Program checks these signs against the assembled path; the Backend independently checks the independently evaluated Geometry interfaces, including position, direction and outer profile. Both interfaces require fixed targets and circular OD checking, allow `same` and `opposed`, and cap position/angular tolerances at `1e-6`.

The numeric Program computes every source segment vector, length and unit tangent. For feasibility only, it groups consecutive edges when exact integer/power-of-two arithmetic on the represented binary64 source coordinates proves a zero cross product and forward direction. A floating multiplication that underflows to zero is not accepted as proof. It never groups a represented nonzero turn; a tiny real corner remains a corner. The original ordered point list is retained unchanged in the solved path and Geometry parameters. Miter and nonadjacent-body checks operate on these maximal forward-collinear chains, so splitting a straight physical span into source edges does not invent a corner or a second pipe body.

For one chain with direction `e`, length `L`, outer radius `r`, previous direction `t_prev` and next direction `t_next`, its start/end plane normals are `n0=t_prev+e` and `n1=e+t_next` (free ends use `e`). For a common cross-section offset `v⊥e` with `||v||≤r`, the two plane positions are `s0(v)=−n0·v/(n0·e)` and `s1(v)=L−n1·v/(n1·e)`. The minimum gap is `L−r||Proj_e⊥(n0/(n0·e)−n1/(n1·e))||`. A negative gap outside binary64 roundoff proves that this selected two-plane miter construction crosses within the chain. A gap at numeric resolution, degenerate plane normal or overflow is `AMBIGUOUS`, not a claimed global impossibility. The old scalar sum of independent corner reaches was removed because it can reject parallel miter planes with a positive common gap.

Exact foldback and nonadjacent chain centerline intersection are rejected. For other nonadjacent chains, the Program first bounds the actual miter sections, including their axial extension beyond the finite centerline endpoints. Disjoint enclosing boxes prove separation. Otherwise, it compares section support intervals along at most the four existing end-plane normals. A strict interval gap proves separation; overlapping intervals leave `AMBIGUOUS/body_overlap_unverified`, without claiming that every construction is impossible. Outward binary64 bounds cover world-to-local subtraction, direction and plane arithmetic, the `n·e` denominators and support evaluation. An unresolved denominator or nonfinite bound cannot admit a pair. The potentially ill-conditioned finite-centerline distance is not used to prove body separation. These checks preserve the complete path, OD, section, miter planes and port contract; they do not introduce smoothing, a 1 mm cutoff or a total-length limit. A numeric `SOLVED` still requires the actual Geometry build and BREP checks.

For `realize`, the first path point anchors the fragment. The first tangent and a stable relative turn define its local axes; an exactly two-endpoint straight path uses `[0,0,0]` and `[length,0,0]`. All middle points remain in order in that same local frame. `fragment.local_transform` carries the anchor relative to `product_origin` and the rigid rotation, with scale 1. The Backend applies its existing placement chain once. `endpoint_reference_directions` carries the original two interface references expressed in the local frame, preserving their world roll; it is not recomputed from the new local Z axis. One `IfcPipeSegment` owns one `pipe_body` fragment. The Geometry interface evaluator supplies named `inlet/outlet` frames, and the Family exposes them; no Program-authored port or old instance handle is used.

`standard_model(ctx)` constructs the existing nominal local path `[[0,0,0],[2,0,0],[2,3,0]]` with OD `0.2 m`, creates its two fixed targets internally, and calls the same solver. It reads only the product section, not caller installation targets or middle world vertices. The Backend applies the unchanged `T(product_origin)` to that nominal shape. At O=0 and O=(7,8,9), the standard local shape and local ports remain equal and only the Backend world placement changes. A standard invocation supplies `middle_points_m: []` and section to satisfy the shared public parameter contract; no installation endpoints or OD are required.

## Use and diagnostics

The caller must retain every source point in order and the exact OD provenance when projecting targets. Unknown wall thickness stays `[]`; it cannot be computed from OD or from a neighboring part. The Family's `INFEASIBLE` keys distinguish missing/unsupported fixed endpoints, `endpoint_diameter`, `endpoint_direction`, `zero_segment`, `foldback`, `self_intersection`, `miter_room`, invalid OD and invalid known wall thickness. `AMBIGUOUS` includes `miter_boundary` or `miter_normal` at numeric resolution, technical capacity and unverified nonadjacent body overlap. A valid numeric proposal is still subject to Geometry's native single-solid validation and same-build BREP endface checks.

Current capacity is 126 middle vertices plus two endpoint targets, retaining the 128-point Geometry path capacity. The public/solved/fragment JSON budget is 64 KiB each. The Geometry parameter document limit is 16 KiB, which may bind before 128 very long coordinates; a call must fail explicitly rather than truncate or split the source path. The solved-coordinate minimum/maximum in `definition.json` are the finite IEEE-754 binary64 representable endpoints, not a business coordinate range. IFC length-unit conversion for `product_origin` remains at the existing input boundary; `_m` coordinates are already metres and are not recursively converted.

After future exact registration, the intended call chain is `ifc_geometry_resource_write` → exact Geometry info/read → `ifc_product_family_write` with this Family contract, `main.py` source and exact binding → exact Family info/read → `ifc_product_realization_preview` using `self_geometry` or the approved standard entry. This candidate does not include an alias, a registration write, or an IFC product installation. Preview `SOLVED`, frame `PASS`, or a picture alone does not prove network connection, wall provenance, actual flow passage, or IFC publication.
